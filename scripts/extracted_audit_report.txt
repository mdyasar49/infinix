P15: Bottom line: do not rebuild the entire website first. Fix the technical foundation, sharpen the commercial message, add proof, improve mobile performance, and build a focused search/content strategy.

P23: 4. Problems  - Technical + SEO
P24: Finding #1: Mobile loading is too slow
P25: Evidence: Supplied PageSpeed mobile test: Performance 70, FCP 3.3s, LCP 5.1s, Speed Index 3.7s. The report also flags items such as image delivery, unused/legacy JavaScript and LCP request discovery.
P26: Why this is a problem: The visitor has to wait too long for the main part of the page to appear. On mobile, this can increase abandonment before the user even understands the offer.
P27: Business impact: High. Slower first impression can reduce engagement and lead generation and can worsen user experience on mobile networks/devices.
P28: Recommended fix: Reduce the amount of JavaScript needed at first load, optimise the hero/LCP asset, compress and resize images, remove unused JS, improve caching, and make the main content render earlier.
P29: Developer action: Developer should identify the exact LCP element, then reduce its transfer size and request chain. Use modern image formats, responsive images, width/height attributes, and preload only the actual LCP asset. Split noncritical JS and defer thirdparty code.
P30: How to validate: Rerun PageSpeed on mobile. Target LCP ≤2.5s, while also checking field data in Search Console/CrUX where available.
P31: Priority: P1  - High
P32: Finding #2: The site relies heavily on JavaScript for public content
P33: Evidence: Direct retrieval of the live site can expose an application shell rather than the full marketing content, while searchenginerendered views can show the page content.
P34: Why this is a problem: If a crawler, social preview system, or other consumer does not execute the JavaScript path correctly, the useful content may be harder to access. It also adds work before the user gets the page.
P35: Business impact: High. It creates technical dependency and can increase rendering cost and performance risk.
P36: Recommended fix: Serve important marketing content in the initial HTML using serverside rendering or static generation, then use JavaScript only for interaction.
P37: Developer action: Developer should ensure title, description, canonical, H1, main copy, internal links and essential schema exist in the initial response—not only after JavaScript runs.
P38: How to validate: Compare `curl`/viewsource output against the browser DOM. The initial response should contain the essential marketing content.
P39: Priority: P1  - High
P40: Finding #3: The .com and .com.au domain setup needs cleanup
P41: Evidence: The main site resolves to the .com.au domain, while the SEO evidence also shows http://infogenx.com/, http://www.infogenx.com/ and https://dev.infogenx.com/ in the indexedpage dataset. Prior live review also found internal links still pointing to infogenx.com.
P42: Why this is a problem: Multiple URL versions create extra redirect/canonical decisions and make the preferred site address less clean for users, crawlers and analytics.
P43: Business impact: MediumHigh. It can waste crawl effort and weaken URL consolidation if the signals are inconsistent.
P44: Recommended fix: Choose one canonical public website host and consistently link to it. Redirect old public variants to the preferred host with a permanent redirect.
P45: Developer action: Replace old internal .com links with siterelative links or the final .com.au URLs. Review dev subdomain indexability and robots rules; keep development environments out of search.
P46: How to validate: Crawl all internal links and confirm there are no unintended domain changes or redirect hops.

P112: Business impact: High as a growth signal. AI search is becoming an additional discovery channel for commercial questions.
P113: Recommended fix: Build stronger entity clarity, directanswer content, expert authorship, original research, real case evidence and consistent company facts. Do not rely on an “AI file” alone.
P114: Developer action: Create pages answering questions buyers actually ask: what InfogenX does, who it serves, what systems it integrates, automation costs, project timelines, Odoo vs Zoho vs Microsoft, and expected ROI.

P117: Finding #12: The site needs more answerfirst content
P118: Evidence: The site contains FAQs and explanatory content, but it can be stronger at answering buyer questions in the first paragraph with concise definitions and followed by evidence.
P119: Why this is a problem: Answer engines work with clear, selfcontained passages. Dense marketing copy is harder to quote than direct factual answers.
P120: Business impact: MediumHigh.

P122: Developer action: Build FAQ sections around real sales questions, but keep the answers genuinely useful and visible; use FAQ schema only where appropriate.
